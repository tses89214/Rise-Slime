# Rise & Slime: A Slime Bakery Idle Game

Portfolio side project: an idle game whose events feed a real-time data pipeline
(Kafka → Flink → ClickHouse → custom HTML dashboard).

## Source of truth

- `docs/design.md` — the full design spec (game rules, numbers, event schema,
  architecture, assets, milestones). Read it before starting any task.
- `docs/asset-integration.md` — how assets map onto the screen, pixel scaling rules, palette. Its art section overrides the asset section of the spec (original art only; third-party fonts/audio).
- `docs/design/main-screen.dc.html` — visual reference for the M1 main screen
  (layout, colors, slime states). It is a design mockup, not production code.

If the spec and the code disagree, the spec in `docs/` wins unless a decision
record says otherwise. When a spec decision changes, update `docs/design.md`
and add a short entry to `docs/decisions/`.

## Ground rules (from the spec's "實作原則")

- Game core is pure TypeScript with no rendering dependency, so bots can run it in Node.
- The core never reads the system clock or calls `Math.random()` directly:
  time is passed in, randomness uses a seeded generator.
- Telemetry is switched by `VITE_TELEMETRY`, read via `import.meta.env` at build
  time, so the itch.io build contains no event-sending code.
- Event types and validation live in one shared package (zod); game, bots and
  collector all import it.
- Invalid events go to a dead-letter Kafka topic, never silently dropped.
- Code is MIT. All game graphics are original art in `assets/original/`, generated by
  `tools/sprites/make_sprites.py`: edit the script and regenerate, never hand-edit the PNGs.
  Third-party files (fonts, audio) keep their licenses and are each listed in `CREDITS.md`
  with author, source URL, license and download date, including CC0 ones.
- UI text is English; use the term glossary in the spec for names in code and events.

## Architecture (from the spec)

One TypeScript game core (rules, numbers, save, event interface) shared by three consumers: browser game (Phaser scene + HTML/CSS UI, Vite), headless Node bots, and the itch.io build (no-op telemetry). Local `docker-compose` pipeline: Collector (Fastify + zod) → Kafka → Flink (Flink SQL, PyFlink for custom state) → ClickHouse → standalone HTML dashboard (uPlot). Tests: Vitest. Planned single repo with folders for core, game, bots, collector, dashboard, Flink jobs.

Bots run in two modes: real-time (into Kafka) and fast-forward (write files, for tuning numbers). Offline progress is computed by simulating the elapsed time (8h cap) with the same core logic.

Spec is written in Traditional Chinese; UI text and event/code names are English (glossary in spec).

## Commands

```
npm install
npm test                         # vitest run
npx vitest run -t "4:6:5"        # single test by name
npm run typecheck
npm run dev                      # browser game (telemetry off)
scripts/demo.sh [farm,mill,bakery,lounge]   # dev server + open game with a seeded demo state
VITE_TELEMETRY=true npm run dev  # browser game, events -> VITE_COLLECTOR_URL (default localhost:3000/events)
npm run build                    # itch.io build: no event-sending code
docker compose up -d             # Kafka x2 + Kafka UI (:8080) + ClickHouse (:8123) + Flink (:8081); data kept in volumes, `down -v` wipes
docker compose --profile submit run --rm flink-sql   # first submit of pipeline/flink/job.sql (replays Kafka)
scripts/flink-restart.sh                             # after editing job.sql: savepoint the running job and resume from it, no replay
KAFKA_BROKERS=localhost:9092 npm run collector   # unset KAFKA_BROKERS = print to stdout; also serves the ops dashboard at http://localhost:3000/dashboard
npm run bots -- --bots 20 --seconds 600 --url http://localhost:3000/events   # or --out file.jsonl; --speed 60 for real-time pacing; --disconnect-rate/--max-buffer for late events
```

## Layout

- `src/core/achievements.ts` — achievement catalogue as pure predicates on `State`; `checkAchievements` is idempotent and records unlocks in `state.achievements`.
- `src/core/sim.ts` — pure simulation (stations, costs, offline progress, M3 merge/traits/slots/feature unlocks, save `migrate`, seeded `rng`). No clock, no `Math.random`.
- `src/events/` — zod `GameEvent` schema (single source of truth) + `makeEmitter` (stamps shared fields, UUID v7; caller passes `now`).
- `src/bots/` — `runBot` (personas: random_assigner, optimizer, quitter) and CLI with duplicate/malformed fault injection.
- `src/collector/` — Fastify `POST /events`; `route()` sends invalid events to `events.dlq`.
- `src/collector/dashboard.ts` + `dashboard/index.html` — read-only `GET /api/dashboard` (fixed ClickHouse queries, incl. latest dead letters) and the uPlot ops dashboard page.
- `docs/system.md` — inventory of every service/port/table/event and how to start and debug them (Traditional Chinese).
- `docs/pipeline.md` — mermaid maps of the services and of every table-to-table hop; read it before touching the pipeline.
- `pipeline/clickhouse/init.sql` (tables, Kafka-engine intake, leaderboard/efficiency/DAU views; runs on first start only), `pipeline/flink/job.sql` (one statement set: events -> `ch.events`; deduped 1-min windows with 15 min allowed lateness -> upsert topics `ch.production_1m` / `ch.pipeline_1m` / `ch.ops_1m`; `ch.late_1m` by `sent_at`). Windowed ClickHouse tables are `ReplacingMergeTree(version)`: read them with `FINAL`.
- `src/game/` (`main.ts` state/render/loop; `audio.ts`, `customers.ts`, `telemetry.ts`, `util.ts`) + `index.html` — plain DOM + CSS-sprite UI (no Phaser), localStorage save + offline progress. Scene is built once; render() caches element refs and only writes text/classes/HTML that changed (otherwise CSS animations restart and layout is invalidated), and skips drawing while the tab is hidden. Customers are small async loops (timers + CSS transforms); each real sale sends one through the shop door. Sprite sheets are scaled by integers (slimes x3; sheet rows = colour, columns = frames, see `assets/original/*.json`). Slime colour follows the job (cosmetic in M1). Art is sized in `--u` (3px desktop, 2px below 1100px), integer only; `?demo=farm,mill,bakery,lounge` seeds a state in dev for screenshots.
- `assets/` is Vite's `publicDir`: served at `/original`, `/fonts`, `/audio`.
- `tools/sprites/` — sprite generator scripts.

## Development Rules

These rules apply to every task in this project unless explicitly overridden.
Bias: caution over speed on non-trivial work. Use judgment on trivial tasks.

### Rule 1 — Simplicity First
Minimum code that solves the problem. Nothing speculative.
No features beyond what was asked. No abstractions for single-use code.
Test: would a senior engineer say this is overcomplicated? If yes, simplify.

### Rule 2 — Surgical Changes
Touch only what you must. Clean up only your own mess.
Don't "improve" adjacent code, comments, or formatting.
Don't refactor what isn't broken. Match existing style.

### Rule 3 — Goal-Driven Execution
Define success criteria. Loop until verified.
Don't follow steps. Define success and iterate.
Strong success criteria let you loop independently.

### Rule 4 — Use the model only for judgment calls
Use me for: classification, drafting, summarization, extraction.
Do NOT use me for: routing, retries, deterministic transforms.
If code can answer, code answers.

### Rule 5 — Surface conflicts, don't average them
If two patterns contradict, pick one (more recent / more tested).
Explain why. Flag the other for cleanup.
Don't blend conflicting patterns.

### Rule 6 — Read before you write
Before adding code, read exports, immediate callers, shared utilities.
"Looks orthogonal" is dangerous. If unsure why code is structured a way, ask.

### Rule 7 — Tests verify intent, not just behavior
Tests must encode WHY behavior matters, not just WHAT it does.
A test that can't fail when business logic changes is wrong.

### Rule 8 — Checkpoint after every significant step
Summarize what was done, what's verified, what's left.
Don't continue from a state you can't describe back.
If you lose track, stop and restate.

### Rule 9 — Match the codebase's conventions, even if you disagree
Conformance > taste inside the codebase.
If you genuinely think a convention is harmful, surface it. Don't fork silently.

### Rule 10 — Fail loud
"Completed" is wrong if anything was skipped silently.
"Tests pass" is wrong if any were skipped.
Default to surfacing uncertainty, not hiding it.
